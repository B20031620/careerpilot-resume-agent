# 面试架构问题回答方案

> 本文档整理了项目可能被问到的架构设计问题，每个问题给出"回答要点"和"避坑提示"。

***

## 1. 为什么用 LangGraph 而不是直接写 Python 逻辑？

**回答要点：**

这个项目有明显的状态流转——简历解析后才能做匹配，匹配报告生成后才能做润色，模拟面试需要多轮循环。这些用 if-else 也能写，但 LangGraph 带来三个好处：

1. **状态机可视化**：图的结构就是业务逻辑的文档，新同事看一眼图就知道流程
2. **条件分支编码在边里**：比如面试 agent 的 `classify_answer → decide_strategy`，决策逻辑不在代码里散落，而是声明式地定义在图的边上
3. **Checkpoint 开箱即用**：面试是多轮交互，需要暂停恢复甚至重放，LangGraph 的 checkpointer 直接支持，不用自己实现状态持久化

**避坑：** 不要说"因为 LangGraph 是新技术所以用"。要说"因为业务场景需要状态机 + 条件分支 + 暂停恢复，LangGraph 刚好解决这些"。

***

## 2. 面试 agent 为什么是循环图而不是 DAG？

**回答要点：**

真实面试不是问完 N 题就结束。面试官会根据你的回答质量动态调整策略：

- 回答薄弱 → 降低难度追问同一话题，探测真实水平底
- 回答中等 → 同难度追问细节，挖掘深度
- 回答出色 → 换话题出更难题，探测能力边界

这个决策逻辑编码在图的条件边里。如果用 DAG（有向无环图），每道题是独立的，无法根据前一道题的评估结果调整下一道题的策略。循环图让图本身编码了面试策略，而不是在代码里写 for 循环 + if-else。

**避坑：** 不要只说"因为需要循环"。要说"因为出题策略需要根据回答质量动态调整，循环图的条件边编码了这个策略逻辑"。

***

## 3. RAG 是怎么用的？跟普通 RAG 有什么区别？

**回答要点：**

普通 RAG 是"检索相关文本拼进 prompt"，但不同 agent 需要的上下文完全不同。我做了分层检索策略：

- **面试 agent**：按技能/项目维度检索。出题时不是拿整份简历，而是拿当前话题最相关的 2-3 段经历。比如简历写了"用 Redis 做缓存"，面试官追问 Redis 缓存策略，而不是泛泛问"你用过 Redis 吗"
- **润色 agent**：按表述相似度检索。检索之前被润色过的相似表述，保证建议风格一致——不会这次建议用 STAR 法则，下次建议用 PAR 法则
- **职场沟通**：按职位身份检索。检索用户的职位级别和行业，生成邮件草稿时贴合身份——不会给应届生出总监级的措辞

**避坑：** 不要说"我用了 RAG 技术增强检索"。要说"不同 agent 有不同的检索策略，这保证给 LLM 的是精准上下文而不是一坨文本"。

## 4. validate\_risks 节点是什么？为什么要做二次验证？

**回答要点：**

润色 agent 生成建议后，有一个 `risk_gate` 节点做风险门控：

- 只对 `risk_level=high` 的建议走 LLM 二次验证（LLM-as-Judge 模式）
- 全部 `low/medium` 的建议直接跳过验证

这是 **LLM-as-Judge** 模式——用 LLM 审查 LLM 的输出。为什么要做？因为润色建议可能包含"建议编造一段实习经历"这类高风险内容，单次生成无法保证安全。

为什么只审查高风险？因为每次 LLM 调用都有成本和延迟。全量审查等于双倍成本，而 90% 的建议是措辞优化（低风险），不需要审查。风险分级让审查成本集中在真正需要的地方。

**避坑：** 不要说"我加了一个验证节点"。要说"风险门控 + LLM-as-Judge，只对高风险建议做二次验证，体现了成本意识和安全分级思维"。

## 5. Tool Calling 有什么好处？为什么不直接在节点里查数据库？

**回答要点：**

直接在节点里查 DB 最容易写，但把数据获取抽成 Tool 有三个好处：

1. **可测试**：Tool 可以 mock，节点函数只测 LLM 决策逻辑。如果节点里混着 DB 查询，测试时需要准备真实数据库
2. **可复用**：`search_history_tool` 在面试和润色 agent 里都能用，不用每个节点重复写 RAG 检索逻辑
3. **可观测**：LangSmith 里每个 tool call 都有独立 trace，排障时能清楚看到哪个数据获取慢、哪个返回了意外结果

这是标准的 Agent 模式：节点只做 LLM 决策，数据获取和持久化通过 Tool 完成。职责分离让代码更清晰、更易维护。

**避坑：** 不要说"因为 LangGraph 支持 Tool Calling 所以用"。要说"职责分离让节点可测试、Tool 可复用、调用可观测"。

## 6. Checkpoint 是怎么用的？

**回答要点：**

面试是多轮交互——用户回答一道题，系统评估后出下一题，中间需要等待用户输入。用 LangGraph 的 `SqliteSaver` 做 checkpoint：

- 每个节点执行后自动保存状态快照
- 用户提交回答时，用 `thread_id` 恢复上次状态继续执行
- 面试可以暂停（关闭浏览器）和恢复（重新打开继续）

但 checkpoint 不只是暂停恢复。LangGraph 的 checkpoint 支持从任意节点重放——如果面试结果不好，可以从第 3 题的 checkpoint 重放，换一条分支走。这比简单的暂停恢复高级得多，相当于给 agent 执行加了"时间旅行"能力。

**避坑：** 不要只说"支持暂停恢复"。要说"时间旅行——可以从任意 checkpoint 重放，换一条分支走"。

## 7. 为什么用豆包 embedding 而不是本地模型？

**回答要点：**

两个原因：

1. **DeepSeek 没有 embedding API**：项目默认用 DeepSeek 做 LLM，DeepSeek 目前不提供 embedding 服务
2. **豆包是国产 API，延迟低**：火山方舟的 embedding API 在国内访问稳定，延迟低，不需要翻墙。用 OpenAI 的 embedding API 就多一个网络依赖

选豆包 embedding 的好处：

- 中文优化，向量质量好
- API 调用，不占本地算力
- OpenAI 兼容接口，切换成本低

**避坑：** 不要说"因为免费"。要说"国产 API 延迟低、中文优化好、OpenAI 兼容接口切换成本低"。

***

## 8. 为什么用 ChromaDB 而不是 FAISS/Pinecone？

**回答要点：**

选 ChromaDB 是因为它是 SQLite 级别的轻量向量库——pip install 即用，数据持久化在本地文件，不需要额外启动服务。适合 MVP 和个人项目。

和 FAISS 比：FAISS 纯内存，重启后数据丢失，需要自己实现持久化。ChromaDB 内置持久化。

和 Pinecone/Qdrant 比：它们是独立服务，需要额外部署和 API key。MVP 阶段不需要分布式向量库。

如果后续要上生产，可以替换成 pgvector（和 PostgreSQL 一起用）或 Qdrant（性能更好），因为 RAG 服务层有抽象，换底座只需要改 `vector_store.py`。

**避坑：** 不要说"因为 ChromaDB 最好"。要说"MVP 阶段够用，生产可替换，因为服务层有抽象"。

***

## 9. 你怎么保证 LLM 输出的结构化？

**回答要点：**

两层保障：

1. **Prompt 层**：每个 prompt 都定义了 JSON schema，要求 LLM 按格式输出
2. **代码层**：用 OpenAI 兼容接口的 `response_format={"type": "json_object"}` 强制 JSON 输出

如果 LLM 输出格式异常，有 fallback 逻辑——比如面试报告生成失败时，从已评估的 turn 数据直接计算分数，不依赖 LLM 输出。

**避坑：** 不要说"我用了 JSON mode"。要说"Prompt + JSON mode 双层保障，加上 fallback 兜底"。

***

## 10. 如果 LLM 调用失败怎么办？

**回答要点：**

每个节点都有错误处理：

- LLM 调用失败 → 设置 `state["error"]`，图的 `_should_stop` 条件边会走到 `END`，不会卡在中间
- 面试出题失败 → 返回错误信息，前端可以重试
- 润色失败 → 保留原始简历，不会因为 AI 失败而丢失用户数据
- 报告生成失败 → 有 fallback 逻辑，从已有数据直接计算

关键原则：**AI 是增强，不是必需**。即使 LLM 不可用，用户的核心数据（简历、面试记录）不会丢失。

**避坑：** 不要说"我加了 try-except"。要说"AI 是增强不是必需，核心数据不依赖 LLM"。

***

## 11. 你的项目架构怎么保证可扩展？

**回答要点：**

三层抽象：

1. **LLM Provider 抽象**：`DeepSeekProvider` 实现了统一接口（chat/chat\_sync/chat\_stream\_sync），要换模型只需要加一个 Provider 实现
2. **RAG 服务层抽象**：`RAGService` 封装了检索策略，换向量库只需要改 `VectorStore` 实现
3. **Agent 图解耦**：每个 agent 是独立的 LangGraph 图，新增 agent 只需要新建 `agents/xxx/graph.py`，不影响其他 agent

**避坑：** 不要说"我用了设计模式"。要说"三层抽象让模型、向量库、agent 都可以独立替换"。

***

## 12. 你觉得这个项目还有什么可以改进的？

**回答要点（展示你有思考但不过度自谦）：**

1. **流式输出**：当前面试 agent 是同步返回，可以改成 `compiled.stream()` 逐节点流式输出，用户能看到"正在评估回答..."的过程
2. **多模型对比**：润色建议可以用不同模型生成多个版本，让用户选择最满意的
3. **Human-in-the-loop**：润色的高风险建议可以走 LangGraph 的 interrupt 机制，暂停等用户确认后再继续
4. **评估体系**：用 LLM-as-Judge 对面试题目质量做自动评估，形成闭环优化

**避坑：** 不要说"代码写得不够好"。要说具体的、可落地的改进方向。
