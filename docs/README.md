# CareerPilot — AI 求职助手

> 一个基于 LangGraph + RAG + LLM 的 AI Agent 求职助手。不是简单的"ChatGPT 套壳"——上传简历后，AI 能像真正的面试官一样根据你的真实经历出题、评估、追问，也能像专业的简历顾问一样分析问题、给出修改建议并自动审查不合规内容。项目从 Agent 编排、知识检索、中断恢复到安全审查，完整展示了一个 AI Agent 系统的设计思路和工程落地。

***

## 一、项目能做什么

上传简历之后，CareerPilot 能帮你做四件事：

| 功能   | 一句话描述                          |
| ---- | ------------------------------ |
| 智能解析 | 自动提取教育、工作、项目、技能，结构化成可视化卡片      |
| 模拟面试 | AI 根据你的真实经历出题，动态调整难度，评估回答并生成报告 |
| 简历润色 | 逐项分析问题给修改建议，自动审查高风险建议防止编造经历    |
| 职场沟通 | 按场景和语气生成沟通草稿 + 避坑提示            |

## 二、功能说明

### 2.1 简历上传与解析

拖拽或点击上传 DOCX/TXT/MD 文件，AI 自动完成两轮解析：

- **第一轮：快速提取**（无需 AI，秒级完成）。用规则匹配姓名、电话、邮箱、教育背景、技能关键词
- **第二轮：AI 精修**（DeepSeek LLM）。把原始简历发给 AI，告诉它"你是一个简历解析专家，请按这个格式输出"，AI 将散乱文本整理成结构化信息。为了保证 JSON 一定正确，做了三层保障：
  1. **格式约束** — 调用 DeepSeek 时开启 JSON 模式，API 层面强制只输出合法 JSON
  2. **Schema 归一化** — 经过统一处理函数：字段缺失补默认值、类型不对做转换、嵌套标准化
  3. **失败兜底** — AI 异常时保留快速提取结果，用户看到的不是空白而是"初步解析"

解析结果以卡片展示：基本信息、教育经历、工作经历、项目经历、技能标签。解析完成后自动存入向量数据库，为后续面试和润色做准备。

### 2.2 AI 模拟面试

选一份已解析的简历，设定题目数量，AI 开始面试。用户视角的体验是：

- 第一道题就直接针对你简历里的具体经历发问，不是泛泛的"介绍一下你的项目"
- 每答完一题，AI 给出分数（0-100）+ 优势 + 改进建议
- 下一题的难度和方向会根据你上一题的表现动态调整——答得好加难度换话题，答得差降难度追问基础
- 面试结束生成综合报告：平均分、核心优势、待改进项、风险提醒、准备建议

### 2.3 简历润色

选一份简历（可附上目标岗位 JD），AI 逐项给出润色建议：

- 每条建议包含：原文、问题、修改建议、修改理由、风险等级（low / medium / high）
- 高风险建议自动过 AI 二次审查，判定是否涉及编造经历、虚假数据——不合规则降级或移除
- 低风险建议（措辞优化类，占 90%）直接通过，不浪费审查成本

### 2.4 职场沟通助手

选场景（回复 HR、薪资谈判、离职沟通等 7 种）+ 语气（专业 / 礼貌 / 坚定 / 简洁），AI 流式生成沟通草稿，输出分正文和避坑提示两部分。

## 四、Agent 是怎么设计的（核心章节）

很多人觉得 AI Agent 就是调个 LLM API。实际上，一个真正有用的 Agent 需要在**编排、检索、安全、状态管理**四个层面做设计。下面逐个拆解。

### 4.1 面试 Agent：用 LangGraph 把面试策略编成一张图

**不用 LangGraph 的做法**：写一个 for 循环，依次出题、收答案、调 LLM 评分，最后算平均分。流程是死的，6 道题和 3 道题的逻辑没有任何区别。

**我们的做法**：用 LangGraph 的 StateGraph 定义一个有向图。图里每个节点是一个纯函数——接收当前状态，返回部分更新。边定义了节点间的流转方向，条件边根据运行时数据决定走哪条分支。

#### 图的完整结构

```
                        ┌─────────────────────────────┐
                        │     init_interview           │
                        │  从数据库加载简历文本          │
                        │  初始化难度级别、话题覆盖      │
                        └─────────────┬───────────────┘
                                      │
                                      ▼
                        ┌─────────────────────────────┐
                        │   generate_question          │
                        │  调 RAG 检索相关经历          │
                        │  拼 Prompt → 调 LLM 出题      │
                        └─────────────┬───────────────┘
                                      │
                              ╔═══════╧═══════╗
                              ║  interrupt   ║  ← 图在此暂停，等用户回答
                              ╚═══════╤═══════╝
                                      │ 用户提交答案后恢复
                                      ▼
                        ┌─────────────────────────────┐
                        │   evaluate_answer            │
                        │  调 LLM：评分 + 优势 + 不足    │
                        │  将本轮结果记入 turns 列表     │
                        └─────────────┬───────────────┘

                        │   decide_strategy            │
                        │  更新 topic_coverage         │
                        │  调整 difficulty_level       │
                        │  本轮不路由，由条件边决定     │
                        └─────────────┬───────────────┘
                                      │
                          ┌───────────┼───────────┐
                          │           │           │
                     "weak"      "medium"     "strong"
                          │           │           │
                          ▼           ▼           ▼
              ┌──────────────┐ ┌────────────┐ ┌────────────────────┐
              │probe_easier  │ │follow_up_  │ │switch_topic_harder │
              │降难度，同话题 │ │detail      │ │换话题，提难度       │
              │出更简单的题   │ │同话题追问  │ │出更有挑战的题       │
              └──────┬───────┘ │挖掘细节     │ └─────────┬──────────┘
                     │         └─────┬──────┘           │
                     │               │                  │
                     └───────────────┼──────────────────┘
                                     │
                                     ▼
                        ┌─────────────────────────────┐
                        │   next_question              │
                        │  current_question_index += 1 │
                        └─────────────┬───────────────┘
                                      │
                          ┌───────────┴───────────┐

                    index < target           index ≥ target
                    (题目没问完)              (题目问完了)
                          │                       │
                          ▼                       ▼
              回到 generate_question        ┌──────────────┐
              继续下一轮                     │ final_report │
                                            │ 汇总所有轮次  │
                                            │ 调 LLM 出报告 │
                                            └──────┬───────┘
                                                   │
                                                   ▼
                                                 END
```

#### 每一个节点做了什么

**init\_interview** — 初始化。从 SQLite 加载简历原文和 JD，设置初始难度为 medium、连续弱回答次数为 0、已覆盖话题为空列表。不调 LLM，纯数据准备。

**generate\_question** — 出题。这是唯一需要 RAG 的节点。先从 ChromaDB 检索跟当前话题最相关的 2-3 段简历经历，然后把检索结果、简历摘要、对话历史、当前难度级别一起拼进 Prompt，调 DeepSeek 生成题目。输出当前题目和题目类型。

**evaluate\_answer** — 评估。把当前题目、用户答案、历史对话拼进 Prompt，调 DeepSeek 输出 JSON 格式的评估结果（分数、优势列表、改进建议、风险点、是否需要追问、追问问题）。同时把本轮完整记录追加到对话历史列表，确保最终报告能拿到完整数据。

**classify\_answer** — 分类，不调 LLM。纯粹做数学判断：分数 < 50 标记为 weak，连续弱回答计数 +1；50-74 标记为 medium，计数清零；≥ 75 标记为 strong，计数清零。这个节点是策略路由的决策依据。

**decide\_strategy** — 决策，不调 LLM。记录已覆盖的话题类型、根据分类结果调整难度级别（weak 降为 easy，strong 升为 hard，medium 保持）。它本身不做路由——路由交给下一条条件边。

**三个策略分支** — probe\_easier（降难度追问）、follow\_up\_detail（同话题深挖）、switch\_topic\_harder（换难题）。核心逻辑都是调 LLM 出一道新题，区别只在于 Prompt 里的引导语不同：降难度分支让出题更友好，深挖分支让追问细节，换题分支强制提升难度出系统设计题。

**next\_question** — 计数器加一，纯数学操作。

**final\_report** — 汇总所有轮次的评估结果，调 DeepSeek 生成综合报告。LLM 调用失败时从已有评分数据直接计算平均分和汇总，不依赖外部服务。

#### 条件边：图怎么决定走哪条路

条件边是 LangGraph 的核心能力。图的每个节点出口不是固定的，而是由一个路由函数在运行时决定。路由函数读取当前状态中的分类结果和连续弱回答次数：

- 连续两次 weak → 不再追问，直接走 final\_report 出报告
- 当前分类为 weak → 走 probe\_easier 降难度追问
- 当前分类为 strong → 走 switch\_topic\_harder 换难题
- 当前分类为 medium → 走 follow\_up\_detail 同话题深挖

路由函数返回的是一个字符串（目标节点名），图引擎根据这个字符串找到对应的节点继续执行。这个映射关系在图定义时用 add\_conditional\_edges 声明——输入是源节点名和路由函数，输出是字符串到目标节点的映射表。

#### 整个图共享一个状态

所有节点共享同一个 InterviewState（TypedDict 定义）。每个节点函数返回一个字典，LangGraph 自动把它合并到全局状态中。比如 classify\_answer 返回分类结果和连续弱回答计数，这两个字段立即对后续所有节点可见，不需要传参。

状态的关键字段和流转：

| 字段                     | 类型   | 谁写入                       | 谁读取                            |
| ---------------------- | ---- | ------------------------- | ------------------------------ |
| current\_question      | str  | generate\_question / 策略分支 | evaluate\_answer、前端展示          |
| eval\_score            | int  | evaluate\_answer          | classify\_answer、final\_report |
| answer\_classification | str  | classify\_answer          | decide\_strategy、条件边           |
| difficulty\_level      | str  | decide\_strategy          | generate\_question（影响出题难度）     |
| topic\_coverage        | list | decide\_strategy          | generate\_question（避免重复话题）     |
| consecutive\_weak      | int  | classify\_answer          | 条件边（连续弱→提前结束）                  |
| turns                  | list | evaluate\_answer（每轮追加）    | final\_report（汇总报告）            |

**为什么用图而不是写代码**：面试策略（什么时候追问、什么时候换题、什么时候降难度、什么时候提前结束）不是散落在函数里的 if-else，而是直接声明在图的边和路由函数里。图本身就是面试策略的文档。

### 4.2 中断-恢复：面试的"时间旅行"

面试是多轮对话——每出一道题，Agent 必须停下来等你输入。LangGraph 的 interrupt\_before 机制原生支持这种模式。

做法是：编译图时设置"在 evaluate\_answer 之前中断"，同时配置 SqliteSaver 把状态持久化到 SQLite。开始面试时，图运行到出完第一道题后自动暂停，把当前状态写入检查点。用户提交答案时，先用 update\_state 把答案注入检查点状态，然后 invoke 继续执行——图从暂停处恢复，运行 evaluate\_answer → classify\_answer → decide\_strategy → 策略分支 → next\_question → generate\_question，到下一个 evaluate\_answer 前再次暂停。

每次暂停时整个图的状态（题目、分数、已问数量、难度级别、分类历史）都持久化。关掉浏览器再打开，图能从上次的暂停点继续执行。这个机制不只是"暂停恢复"，它意味着可以从任意历史检查点重新执行——比如回到第 3 题，换一条策略分支重走。

### 4.3 RAG：让 AI 出的题跟你有关

没有 RAG 时，AI 看到的只是你的简历全文，出的题往往是泛泛的"你用过什么技术"。

我们的做法：在出题节点执行前，先从向量库检索跟当前话题最相关的经历片段，拼进 Prompt。

流程是：简历解析完成后，把每段经历（工作、项目、技能）通过豆包 Embedding API 转成 2048 维向量存入 ChromaDB。面试出题时，把当前话题也转成向量，在库中搜索最相似的 2-3 段经历，拼进 LLM 的 Prompt。

实际效果对比：

- 无 RAG："请介绍一下你的项目经历"
- 有 RAG："你在图像增强研究中使用 PyTorch 做了哪些实验设计？你的方法相比传统方法有什么优势？"

**不同场景用不同检索策略**，不是一套逻辑到处套：

| 场景   | 检索目标      | 为什么          |
| ---- | --------- | ------------ |
| 面试出题 | 简历经历和项目片段 | 出跟用户真实经历相关的题 |
| 简历润色 | 历史润色建议    | 保持修改风格一致     |
| 职场沟通 | 用户职位和行业信息 | 生成贴合身份的草稿    |

### 4.4 LLM-as-Judge：让 AI 审查 AI

润色生成的建议中，有的只是措辞优化（低风险），有的可能涉及"建议补充一段实习经历"（高风险，可能等于编造）。

我们用风险门控 + LLM 二次审查来解决：

AI 生成润色建议时，每条都标注风险等级。然后走一个 risk\_gate 节点做分流——有高风险建议时走 validate\_risks 节点用 AI 二次审查判断是否合规（不合规则降级或移除），没有高风险建议时跳过审查直接生成最终报告。

**为什么不全量审查**：每次 LLM 调用有成本和延迟。90% 的建议只是措辞优化不需要审查。风险分级让审查成本只花在真正需要的 10% 上。

### 4.5 Tool Calling：职责分离

节点函数只做 LLM 决策，数据获取和持久化交给 Tool：

| 节点（纯决策）            | Tool（数据操作）                       |
| ------------------ | -------------------------------- |
| generate\_question | search\_history\_tool（查 RAG 向量库） |
| init\_interview    | load\_resume\_tool（查 SQLite）     |
| final\_report      | save\_report\_tool（写 SQLite）     |

三个好处：Tool 可 mock 让节点逻辑可独立测试；同一个 search\_history\_tool 在面试和润色里都能用；每个 Tool 调用在 LangSmith 里都有独立的 trace 可追踪。

### 4.6 LangChain 的角色

LangChain 在这个项目里负责连接 LLM 的"管道"工作：从 YAML 文件加载 Prompt 模板、填入变量、输出 messages 列表；所有节点通过同一个接口调 DeepSeek，换模型只需换 provider。

## 五、怎么保证输出可靠

AI 输出是概率性的，不能 100% 信任。项目在每层都做了兜底：

| 场景      | 正常路径             | 兜底方案                 |
| ------- | ---------------- | -------------------- |
| 简历解析    | DeepSeek 返回 JSON | 保留规则提取结果，显示"初步解析"    |
| 面试出题/评估 | DeepSeek 生成      | Mock 模式用预设数据，不依赖 API |
| 报告生成    | DeepSeek 汇总      | 从已评估数据直接计算分数         |
| 润色审查    | DeepSeek 二次验证    | 审查失败保留原有风险标记         |

核心原则：**AI 是增强，不是必需**。LLM 不可用时核心功能仍然可用，用户数据不会丢失。

## 六、怎么写测试（测试开发岗位重点）

项目当前有 67 个后端测试用例。对测试开发岗位来说，面试官关心的不是数量，而是**怎么设计测试策略**和**怎么解决"AI 不可控"这个核心难题**。

### 6.1 核心难题：依赖 LLM 的代码怎么测

Agent 的每个节点都调 DeepSeek API。如果测试也调真实 LLM，会有三个致命问题：花钱、慢（API 调用 1-3 秒）、不稳定（同一输入可能返回不同输出，结果不可复现）。

**解决思路：测试替身——Mock 模式**

核心思路是把"调用 LLM"这个不稳定环节替换掉，让测试聚焦在真正需要验证的东西上——Agent 的编排逻辑。

做法是设置一个 mock 开关。所有节点函数在调用 LLM 之前先检查这个开关：如果开启，直接返回一套预先定义好的假数据，跳过网络请求。这套假数据和真实 LLM 返回的 JSON schema 完全一致（字段名、类型、嵌套结构完全相同），所以测试覆盖了完整的数据流转链路（节点执行 → 状态合并 → 条件路由 → 下一节点触发），只是把最不稳定的 LLM 调用换成了确定性的替身。

这本质上是经典测试模式中的 Stub（桩）——用一个返回固定值的替代实现来替换外部依赖。只不过这里被替换的不是数据库，而是 LLM 的推理过程。

### 6.2 测试分层策略

| 层级    | 覆盖范围                                   | 使用技术                                      | LLM 依赖       |
| ----- | -------------------------------------- | ----------------------------------------- | ------------ |
| 单元测试  | Schema 校验、数据模型 CRUD、JWT 签发/校验          | pytest                                    | 无            |
| 集成测试  | HTTP 请求 → FastAPI → LangGraph 图执行 → 响应 | pytest-asyncio + httpx AsyncClient + Mock | Mock 模式      |
| 端到端测试 | 浏览器全流程                                 | 暂未覆盖                                      | 真实 LLM（人工验收） |

单元测试覆盖确定性逻辑，不依赖 LLM。集成测试是核心——用异步 HTTP 客户端模拟前端请求，每个测试用例如同一个完整的用户操作，但因为开了 Mock 模式，不走真实 LLM 但图的流转全部真实执行。

### 6.3 测试具体覆盖了什么

**接口对不对**：创建成功是不是返回 201？查不到是不是返回 404？参数错了是不是返回 422？

**Agent 图有没有真的跑起来**：调完创建面试接口，检查返回里有没有生成第一道题、有没有创建第一轮对话记录。

**策略路由走对了没有**：Mock 模式固定返回 78 分，属于"中等回答"。测试断言下一题走的是同话题追问而不是降难度或换难题。Mock 的价值就在这里——让原本随机的 LLM 输出变得确定，路由结果可以断言。

**暂停和恢复灵不灵**：连着调两次接口模拟完整的"出题 → 作答"交互。第一次确认状态里有题但没有评分（停在了等用户输入的地方），第二次确认评分出来了、下一题也生成了。

**题问完了会不会自动结束**：设两题目标，答完两道后检查状态是否自动变成已结束、最终报告是否生成。

**出错了能不能兜住**：模拟没配 Key 的场景，验证接口返回的是参数错误（422）而不是服务器内部错误（500）。

**LLM 挂了报告还能不能出**：验证报告节点在调不到 LLM 时，能从前面已经存好的评分数据直接算平均分、汇总优势不足。

### 6.4 为什么没测真实 LLM 调用

面试官大概率会问："你的测试不调真实 LLM，怎么知道 LLM 输出是对的？"

回答逻辑：**自动化测试测确定性逻辑，非确定性输出靠其他机制保障**。LLM 返回是概率性的——同一个 Prompt 两次返回可能不同，不适合放进要求结果可复现的自动化测试。正确做法是分层保障：自动化测试负责 Agent 编排逻辑（图流转、条件路由、状态合并），这部分是确定性代码；LLM 输出质量靠 Prompt 版本管理（每次改 Prompt 在开发环境手动验证）+ 浏览器全流程验收。这和前端项目不把 UI 像素对比放进单元测试是一个道理——不是不测，是测的地方不对。

**如果能重来的改进方向**：

1. **混沌测试**：模拟 LLM 返回各种异常（空字符串、非 JSON、字段缺失），验证每个节点的兜底逻辑
2. **参数化 Mock**：注入不同的 mock 分数走遍三条策略分支，覆盖完整条件路由
3. **性能回归**：记录面试完整流程的端到端耗时基准，Prompt 变长或模型变慢时自动告警

## 七、AI 辅助编程，怎么保证代码质量

项目大量使用 AI（Claude Code）辅助开发。面试官大概率会问："AI 写的代码你能放心吗？怎么保证质量？"

这个问题 2025-2026 年在开发圈讨论非常激烈。业界已经从"vibe coding 爽就完了"进化到了"viable coding 要能上生产"。核心问题不是用不用 AI，而是用什么流程让 AI 的快和代码的稳兼得。

### 业界主流做法

**Blue-Red 双 Agent 模式**：一个 Agent 专门生成代码（Blue），另一个 Agent 专门审查代码（Red）。Red Agent 不只是跑 linter，而是检查需求是否满足、验证逻辑是否正确、标记漏掉的边界处理。本质上是把 code review 自动化了。

**三级质量门禁**：代码提交前过三道关——静态检查（ESLint/类型检查，拦截约 42% 问题，耗时 < 1 秒）、动态验证（智能测试生成，拦截约 35%，耗时 5-15 秒）、人工聚焦审查（只看 AI 标注的高风险改动块，拦截约 23%，耗时 1-5 分钟）。三道关过完才允许合入。

**渐进式信任机制**：给 AI 设信任分。初始 50 分，每次通过验证 +10，每次人工纠正 -15，出现重大错误 -30。分数 > 80 时 AI 可以直接提 PR，< 30 时强制人工接管。

**可观测性闭环**：不只是人审查 AI 的代码，还要让 AI 自己去查 trace 和日志。代码部署后 Agent 查询生产环境数据来验证自己的改动是否引入了异常。从"人盯着 AI"变成"AI 自己检查自己，人审计检查机制"。

**Vibe Contract（AI 可读规范文件）**：团队维护一份共享的规范文件，里面写清楚命名规范、文件结构、禁用手法、测试要求。所有 AI 工具共享引用这份文件，据反馈可以消除约 70% 的 AI 代码混乱。

**模型人格画像**：不同 LLM 的 bug 倾向不同——有的容易泄露密钥，有的容易引入并发问题。针对不同模型调整不同审查策略。

### 本项目怎么做的

**CLAUDE.md 立规矩（对标 Vibe Contract）**：项目根目录写了四条硬规则——先想再写、简单优先、精准修改、目标驱动。不给 AI 留模糊空间。

**测试兜底（对标质量门禁）**：67 个手写测试用例，Mock 模式保证可复现。AI 改任何代码跑一遍全量测试。

**Prompt 与代码分离 + 图声明式（降低影响半径）**：改 Prompt 不动代码，改代码不碰 Prompt。Agent 图声明式——新增功能加节点加边，不需要重构整张图。AI 改错一个节点不影响图的其余部分。

**人机分工明确**：架构设计、取舍判断、代码 review 是人做；写节点函数、写测试、改 bug 是 AI 做。

### 面试时怎么回答

> "AI 写代码现在业界共识是 'vibe then verify'——快是真的，但不能不做验证。我主要做了三件事。第一，给 AI 立规矩，项目根目录有 CLAUDE.md，写死了不抽象、不改无关代码、先想再写。第二，人和 AI 分工明确，架构设计和取舍是我做，写代码是 AI 做。第三，所有 AI 生成的代码必须通过我手写的 67 个测试用例。这三件事加起来就是：用规矩框住 AI、用测试兜住 AI、把决策权留在自己手里。"

## 八、简历写法

以下是可以直接用在简历中的项目描述，按投递岗位不同准备了两个版本。

### 通用版（后端 / 全栈 / AI 工程）

**CareerPilot — AI 求职助手**（个人项目）

基于 LangGraph + RAG + LLM 的 AI Agent 应用。上传简历后，AI 根据用户真实经历自动出题、动态调整面试策略、评估回答并生成报告；同时支持简历智能解析和润色。

- 使用 LangGraph 构建自适应面试 Agent 图，10 个节点 + 条件边实现三分支动态路由（弱回答降难度追问 / 中等深挖细节 / 强回答换题加难度），替代传统线性循环
- 基于 ChromaDB + 豆包 Embedding 实现分层 RAG 检索，面试出题、简历润色、职场沟通三个场景各自采用不同检索策略
- 引入 LLM-as-Judge 模式：润色建议按风险等级分流，高风险走 AI 二次审查，低风险直接通过，兼顾安全与成本
- 通过 LangGraph interrupt + SqliteSaver 实现面试中断-恢复机制，支持暂停、恢复和从任意检查点重放
- 设计 Mock 模式（Stub 替身）解决 LLM 依赖的测试难题，67 个自动化测试用例覆盖全部图边和错误分支
- 前端 React + TypeScript，后端 FastAPI + SQLite，Prompt 与代码 YAML 分离管理

### 测试开发版（投测开岗位时用）

**CareerPilot — AI 求职助手**（个人项目）

基于 LangGraph + RAG + LLM 的 AI Agent 应用，支持简历解析、自适应模拟面试、智能润色。主要负责测试策略设计和质量保障。

- 针对 LLM 输出不可控的核心难题，设计 Mock 模式（Test Double / Stub）将 LLM 调用替换为确定性替身，确保 Agent 图编排逻辑可复现验证
- 搭建三层测试体系：单元测试（Schema/CRUD/JWT）+ 集成测试（pytest-asyncio + httpx AsyncClient 模拟完整 HTTP → Agent 链路）+ 人工验收（Prompt 效果评估）
- 覆盖 7 个验证维度：API 契约、图执行完整性、条件路由正确性、中断-恢复机制、终止条件、错误边、兜底逻辑
- 引入环境变量开关实现 Mock/真实 LLM 一键切换，测试环境不消耗 API token
- 落地 CLAUDE.md 规范文件约束 AI 生成代码质量，67 个手写测试用例作为 AI 代码合入门禁
- 前端 React + TypeScript，后端 FastAPI + SQLite + LangGraph，测试框架 pytest + pytest-asyncio
